  Linux table: 15200 x 9500 counts, 100 counts/mm, ~133 reports/s.
- Wacom driver 6.4.14-2 is installed and running (TabletDriver, WacomTabletDriver, Wacom_IOManager).
- A scratch probe (scratchpad/pentest/main.swift) logged real pen events in an AppKit window:

  * proximity arrives as `.tabletProximity`-subtyped mouseMoved events: pointingDeviceType 1 (.pen), vendorID 0x56a, tabletID 890 (=0x37A), systemTabletID 1.
  * `absoluteX/absoluteY` are tablet counts with the ORIGIN TOP-LEFT and Y INCREASING DOWNWARD (correlation with window y = -1.0). Observed ranges sat inside 15200 x 9500.
  * side switch → `rightMouseDown/Dragged/Up` with buttonMask 0x2 (tip = 0x1). A second switch did not arrive as a mouse button.
  * reading `.pressure` on a plain `.mouseMoved` (hover) is not safe — only read pressure on mouse down/drag/up and tablet events.

Synchronized root groups: a new .swift file under WriteMind/ or WriteMindTests/ is in the target with no pbxproj edit.
- The notebook's drawing layer (`DrawingCanvas`) is a SwiftUI Canvas + DragGesture, not an NSView. A `Stroke` is {id, colorHex, width, points (normalised 0…1 of the pane, both axes), transform, group}. `InkPaths.path(for:points:)` is the ONE geometry source for both painters (`DrawingCanvas.draw(_ stroke:…)` on screen, `DrawingInk` on paper). Strokes are saved in `.drawings/<note>.json`; `DrawingStore.load` turns a decode failure into an EMPTY drawing, so every new field MUST be `decodeIfPresent`.
- Wacom's macOS Driver Request Interface (MIT, github.com/Wacom-Developer/wacom-device-kit-macos-api; a copy is at scratchpad/wacomapi/) lets an app create a CONTEXT over Apple Events to the driver (signature 'WaCM'): kAECoreSuite/kAECreateElement with keyAEObjectClass = cContext 'CTxt', keyAEInsertHere = tablet routing (cWTDTablet 'Tblt', formAbsolutePosition, index 1-based), 'for ' = context type ('Pos ' default / 'Blnk' blank). The reply's direct object is the context id (UInt32). Set a context property with kAESetData on {formPropertyID <prop>} from {cContext by absolute position = id}… see WacomTabletDriver.m routingTableForContext + setBytes. `pContextMovesSystemCursor` 'Mvsc' (typeBoolean) = false makes "all tablet events … be sent as pure tablet events" and the pen stops moving the system cursor. Contexts only act while the app is frontmost, vanish when it quits, and should be destroyed before quitting (kAEDelete). Tablet properties readable: pXDimension 'Xdim', pYDimension 'Ydim' (typeSInt32), pTabletSize 'Tsiz', pResolution 'Resl', pName. NEVER set a property through the raw tablet routing table — that changes the global tablet for every app.
  Sending Apple Events needs `INFOPLIST_KEY_NSAppleEventsUsageDescription` and the user's one-time Automation consent (a macOS prompt; that click is Sean's).

## The shape of the whole feature

**The Wacom is an INPUT DEVICE, chosen exactly like a camera.** The menu-bar "Input Devices" menu lists the cameras and, under them, any Wacom tablet that is plugged in ("One by Wacom (CTL-472)"). Picking the tablet turns the camera off and the right-hand pane — the one that shows the video — shows THE PAGE instead. Picking a camera goes back to video. The choice is remembered the way `lastCameraDeviceID` is, and the same "a first launch never asks" rule holds: nothing talks to the Wacom driver (no Automation prompt) until the tablet has been picked from the menu at least once.

**The page is "the picture of a page".** A portrait sheet of paper fills the pane at the tablet's shape. The tablet is read ROTATED 90° CLOCKWISE (Sean holds it turned a quarter turn clockwise from the landscape it shipped in): tablet (x, y) in counts, origin top-left, y down, extent (W, H) → page (u, v) normalised, origin top-left: u = 1 − y/H, v = x/W, and the page's aspect (width ÷ height) is H/W (9500/15200 = 0.625). A quarter-turn setting (like the camera's rotate buttons) holds this; its default is one quarter turn clockwise and it is remembered.

While the tablet is the chosen input and WriteMind is frontmost, a driver context with Mvsc = false keeps the pen from moving the system cursor: the pen is a writing instrument on the page, not a pointer. A hover marker on the page shows where the nib is. The trackpad/mouse still drives the UI.

Writing on the page: pen tip down = ink (pressure-shaped, natural — see Phase 1). Tapping = a dot (i, j, full stops). The page persists across launches in Application Support (NOT in ~/Documents/WriteMind — that folder is Sean's notes). Undo/redo/clear for the page.

**Anything drawn can be selected and inserted.** Holding the pen's side switch and dragging on the tablet draws a selection box on the page (so does a plain mouse/trackpad drag on the page). The box offers the same three choices the camera's section box does (`SectionBox` in CameraPane.swift): **Image** (the region as a picture, paper and all), **Writing** (the strokes themselves, as vector strokes in the note's drawing layer — crisp, pressure and colour kept), **Text** (the ink rendered black on white and read by `TextRecognition`, then inserted like the camera's Text). Placement follows the camera's rules (`NotebookCapture.placement`, under the caret via `placedCenter`), so a tablet capture lands at the same scale as a camera capture.

**Themes, pens and colours on the page.** Paper themes: Plain, Dot grid, Ruled, Graph, Legal (yellow, ruled, red margin), Blackboard (dark). Pens: a set of `InkTool`s — Pen (ballpoint), Fountain, Pencil, Marker, Brush — each a different pressure response/thinning/taper/opacity. Colours: the app's preset swatches plus a ColorPicker. All remembered.

**The separate mode: the Wacom draws IN THE NOTEBOOK.** A switch on the tablet pane: "Write on: Page | Notebook". In Notebook mode the rotated tablet maps onto the visible notes pane and the pen writes straight into the note's drawing layer with the same natural ink, tool and colour; the hover marker shows over the notes. The side-switch drag selects there (the drawing layer's marquee). The page is untouched while this is on.

## Phases — ONE SHIP EACH (Sean: deploy after every change; one ask per build)

### Phase 1 — natural ink (the engine, and the notebook's pen gets pressure)
1. `WriteMind/Drawing/InkOutline.swift`: a faithful Swift port of perfect-freehand (Steve Ruiz, MIT — keep the MIT notice and the upstream version in the file header; fetch the TS source with `gh api repos/steveruizok/perfect-freehand/contents/packages/perfect-freehand/src/...`). getStrokePoints + getStrokeOutlinePoints + the option set (size, thinning, smoothing, streamline, easing, simulatePressure, start/end taper+cap, last). Pure; tested in `WriteMindTests/InkOutlineTests.swift` (a straight line's outline is ~size wide in the middle; higher pressure → wider; taper → narrower ends; one point → a dot; empty → empty; no NaN on repeated points).
2. `InkTool` (its own file): pen, fountain, pencil, marker, brush — each maps a stroke's `width` and its pressures to InkOutline options (size factor, thinning, smoothing, streamline, easing, taper) and an opacity. Tune `pen` for HANDWRITING at a 2–4 pt width: firm, slightly pressure-thinned, gentle taper, low lag (streamline ~0.3–0.45), so letters look written with a ballpoint/gel pen, not a felt tip.
3. `Stroke` gains `pressures: [Double]?` (parallel to `points`, 0…1) and `tool: InkTool?` — CodingKeys, memberwise init (default nil), `decodeIfPresent`. EVERY place that rewrites `points` (transform baking, splitting, cropping, merging, copy/paste, InkVector/shape recognition, the Cross model note) must keep `pressures` in lockstep — grep for `.points` writes. Tests: an old sidecar with neither key decodes unchanged; round trip with both.
4. `InkPaths.path(for:points:)`: a stroke with `tool != nil` (or pressures) is the filled InkOutline polygon (smoothed through midpoints like getSvgPathFromStroke), `filled == true`; a legacy stroke (tool nil, no pressures) is EXACTLY what it was. Both painters apply `tool.opacity`. Hit testing keeps working (it reads width). If outline building per redraw is measurably slow with a few hundred strokes, cache by (id, point count, size, transform-free) — measure first.
5. Pressure into the notebook's pen: a tiny `PenSample` reader — a local NSEvent monitor on [.leftMouseDown, .leftMouseDragged, .leftMouseUp, .tabletPoint] that remembers the pressure of the last event whose subtype is `.tabletPoint` (and whether the last event WAS a tablet one). `DrawingCanvas`'s `.drawing` case appends that pressure to `current.pressures` and sets `current.tool = .pen` when the stroke's first event was a tablet event; a mouse/trackpad stroke stays tool nil / pressures nil and draws exactly as today. Make the event→sample decision a pure function over NSEvent and test it with NSEvents built from CGEvents (`CGEvent(mouseEventSource:…)`, set `.mouseEventSubtype` = tablet point (1) and `.mouseEventPressure`, then `NSEvent(cgEvent:)`). The monitor must return every event unchanged.
6. `NSEvent.isMouseCoalescingEnabled = false` once at launch (full-rate pen samples).
7. Docs in the same change: an AGENTS.md rule paragraph (what InkOutline is, the lockstep rule for pressures, the legacy-stroke guarantee), the file map rows, and a `docs/CROSS-PLATFORM.md` entry (the port must read PointerEvent.pressure for pointerType 'pen' and use perfect-freehand with the same options; the sidecar gained `pressures` and `tool`).

## Phase 2 addendum — what is still unknown, and how the code must cope (2026-10-02, after Phase 1 shipped as e611f5f)

Phase 1 is in: `InkOutline`, `InkTool` (pen/fountain/pencil/marker/brush), `Stroke.pressures`/`tool`, `PenSampleReader`, coalescing off at launch. Reuse them; do not build a second ink path. The page draws its strokes through `InkPaths`/`DrawingCanvas.draw(_ stroke:…)` exactly as the notebook does.

Nobody has yet seen, with the real pen, what the driver sends while a context with Mvsc = false is active (it can only be tested with Sean's hand on the pen, after he answers the Automation prompt once). So:
- Take pen data from EVERY route the driver might use, through one funnel (`TabletInput`): native `.tabletPoint`/`.tabletProximity` events AND mouse down/drag/up/moved events whose subtype is `.tabletPoint`/`.tabletProximity`, from a LOCAL monitor (events sent to WriteMind) and a GLOBAL monitor (events sent to other apps — observe only). De-duplicate by event timestamp. Tip down = buttonMask bit 0 or (for native tablet events) pressure > 0; side switch = buttonMask bit 1 (or a rightMouse* event with tablet subtype).
- While the tablet is the input and the page is showing, the LOCAL monitor SWALLOWS (returns nil) every pen event it turns into ink or a selection — so a pen tap never clicks a button or moves the caret under a stray cursor; trackpad/mouse events (no tablet subtype) are always returned untouched.
- If the context could not be made (no driver, Automation refused, Apple Event timeout), the page still works from the events that reach WriteMind, and the pane says one line about why the pen also moves the pointer, with a button that opens System Settings › Privacy & Security › Automation (x-apple.systempreferences:com.apple.preference.security?Privacy_Automation).
- DebugLog (the app's /tmp/writemind-debug.log) gets one line per state change: context created/failed (with the OSStatus), first event of each kind seen (type, subtype, buttonMask, which monitor), proximity in/out. Not one per sample. That is how the first real session gets diagnosed without asking Sean anything.
- The mapping from absolute counts to page fractions, the rotation (quarter turns, default 1 = 90° clockwise), the tip/side-switch/proximity state machine, the stroke building and the selection box are PURE and tested with synthetic samples. The Apple Event descriptor building is tested by inspecting descriptors (no driver needed). Only the actual send is untested, and it is guarded by `TestHost.isActive`.
- Tablet extent: ask the driver (pXDimension/pYDimension of tablet 1); fall back to a table keyed by USB product id (0x037A → 15200 × 9500); and widen to the largest absolute value ever seen, so a wrong table entry can never clip the page.

## CAPTURE addendum (2026-10-02, after Sean's first real sessions) — the driver will not let go of the pointer, so WriteMind takes the tablet itself

Sean: "how can i disable wacom from taking over my mouse?", "i did, it's still controlling my mouse", "shouldn't WriteMind need some permissions like this?", "fix the wacom not being captured by writemind properly issues".

MEASURED on his Mac with the real driver (6.4.14-2) and probes (scratchpad/wacomprobe/*.log):
- The driver's Apple Event interface is READ-ONLY in practice. To 'WaWT' (WacomTabletDriver, com.wacom.wacomtablet): `core/cnte` and `core/getd` answer (tablet count 1; Xdim 9499, Ydim 15199, name "One by Wacom"; pen: pnam "Pen", Pmde 'Absl', Smap = display 2's rect, Oren 'Port'). EVERY write is ignored: `core/crel` for a context returns an empty reply and no context exists afterwards (five variants of the parameters), `core/setd` of the pen's Smap returns an empty reply and the value reads back unchanged (four variants), and the sdef's 'Core' class gets errAEEventNotHandled (-1708). 'WaCM' (TabletDriver.app) only counts tablets. So there is no context, no Mvsc, and no way to remap through the driver. CGAssociateMouseAndMouseCursorPosition(0) does not hold the pointer either (the driver posts absolute positions): measured, 493 pointer moves in 509 pen events.
- The driver's tablet orientation on his Mac is PORTRAIT, so it reports Xdim 9499 × Ydim 15199 — but NSEvent absoluteX/absoluteY stay in the RAW LANDSCAPE frame (x seen up to 13217 > 9499). WriteMind took the driver's dimensions as the extent and then turned them again: the mapping is wrong. The extent must be the RAW sensor's (table by product id: 0x037A → 15200 × 9500), widened by what is seen — never the driver's oriented numbers.
- What WriteMind logs today: both monitors see the pen — native `.tabletProximity` (type 24) and mouse events with tablet subtypes (mouseMoved/Down/Dragged/Up subtype 1, proximity subtype 2). The NSEvent funnel works; only the pointer is the problem (it flies around the driver's mapped display, and a tap outside WriteMind's window clicks whatever is there).
- ioreg with the driver running: the tablet's USB interface 0 carries one HID device with two clients — WindowServer's IOHIDEventServiceUserClient and WacomTabletDriver's IOHIDLibUserClient; interface 1's HID device has no client. The driver also holds an AppleUSBHostDeviceUserClient on the USB DEVICE (control requests), not on an interface, so its reports come through IOHID.

THE FIX: while WriteMind is capturing (a tablet is the chosen input, its target — page or notebook — is on screen, and WriteMind is the active app), WriteMind opens the tablet's HID device(s) with `kIOHIDOptionsTypeSeizeDevice` and reads the pen's raw reports itself. A seized device delivers nothing to the system or to other clients, so the driver goes quiet and the pointer stays where the trackpad left it. When capture ends (app deactivates, target hidden, tablet turned off or unplugged, quit) the device is closed and the driver has it back.
- PERMISSION: opening a mouse-class HID device needs Input Monitoring (TCC ListenEvent). `IOHIDCheckAccess(kIOHIDRequestTypeListenEvent)` reads it without asking; `IOHIDRequestAccess` asks (and lists the app in System Settings › Privacy & Security › Input Monitoring) — ONLY as the direct consequence of Sean picking the tablet, never at launch ("a first launch never asks"). Denied/undecided → the pane's one status line says so with a button that opens `x-apple.systempreferences:com.apple.preference.security?Privacy_ListenEvent`; a grant usually needs the app relaunched before an open succeeds — if access reads granted but the open is refused (kIOReturnNotPermitted), say "quit and reopen WriteMind". Never under TestHost.
- RAW REPORTS (One by Wacom / Bamboo-pen class; reference: Linux drivers/hid/wacom_wac.c `wacom_bpt_pen` and wacom_sys.c `wacom_set_device_mode` — fetch them with gh/curl and port the LAYOUT, not the code; it is GPL): report id 2, 10 bytes: data[1] bits 0x80 in range, 0x40 proximity, 0x20 ready, 0x01 tip, 0x02 side switch 1, 0x04 side switch 2, 0x08 eraser; x = LE16 at 2, y = LE16 at 4 (raw landscape counts, origin top-left, y down — the same frame the mapping already assumes), pressure = LE16 at 6 (0…2047 → 0…1), distance at 8. With the driver running the tablet is already in this mode; with no driver it enumerates as a relative mouse until feature report [0x02, 0x02] (report id 2, mode 2) is set — send it once after a successful seize (idempotent), and log what the first reports look like either way. Treat anything that is not a 10-byte id-2 pen packet as unknown: log the first few in hex, do not guess.
- ONE FUNNEL STILL: raw reports become the same `TabletReading`/`TabletSample`s the NSEvent route makes, through the same `TabletPen` state machine. While raw capture is delivering, the NSEvent route is ignored (no double ink); if tablet NSEvents keep arriving while seized, the driver still hears the tablet — log that once ("driver still posts events while seized") and say in the status line that the pointer may still move.
- If the seize is refused (kIOReturnExclusiveAccess — the driver holds it) or anything else fails, fall back to the NSEvent route exactly as today, with a status line that says the pen also moves the pointer and why, and log the IOReturn in hex. No crash, no hang; opens and closes off the main thread or proven quick.
- The Apple Event context path (`WacomDriver.takeThePen`, the Automation ask, `NSAppleEventsUsageDescription`, the "needs consent/no reply" statuses) cannot work on this driver: REMOVE it from the connection path, the status line and the docs rather than leave a dead ask in front of Sean (delete the code and its tests, or keep only what is still called — no dead code). The driver's process is still worth watching (KVO) only if something uses it.
- DebugLog (one line each, never per sample): access state, each device opened (usage page/usage, IOReturn), mode-set result, the first 12 raw reports in hex, first parsed sample, capture start/stop, any NSEvent seen while seized.
- Pure and tested: the packet parser (tip/switch/range/proximity bits, LE fields, pressure scaling, short or foreign packets rejected), the capture state machine (when to seize and release, against a stand-in device layer), the status line's words, the raw-extent rule (driver's oriented dims never used). The live IOKit calls sit behind a protocol the tests replace, and refuse under TestHost.
